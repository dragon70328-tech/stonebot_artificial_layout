# StoneBot-Artificial-Stone-Layout / MCP

## Scope

The first plugin milestone adds a stable Agent-facing boundary without changing
the existing CLI, API, portal, drawing profiles or nesting algorithms.

```text
Codex / DeepSeek Harness / Claude Code / Kimi Code / Web / CLI
  -> stonebot_* tools
  -> PluginJobService
  -> AgentRuntime + WorkflowSession
  -> existing deterministic Stonebot core
```

MCP 是主协议；各平台插件是薄适配器，不得复制 StoneBot 的识别、排板或校验逻辑。

## Stable workflow

```text
stonebot_analyze_drawing
  -> optional subject listing / correction loop
  -> stonebot_configure_nesting
  -> stonebot_confirm_drawing
  -> stonebot_confirm_nesting
  -> stonebot_finalize_job
```

The three confirmation calls correspond to the existing drawing, board-count
and final-output gates. Agent prose cannot bypass those gates.

## Circular-saw secondary policy

Bridge jobs may include `circular_saw_diameter_mm`, `saw_plunge_extra_mm`
(default 2) and `saw_safety_margin_mm` (default 0).  The core calculates:

```text
H = thickness + plunge_extra
clearance = sqrt(diameter * H - H * H) + safety_margin
```

The result is an internal-plunge clearance, not a global `min_gap` and not
kerf.  It is compared only after total sheet count: minimum sheets always win,
then same-count layouts with fewer insufficient reflex cut points win.  A
clearance deficit is reported but never silently adds another sheet.

## Harness portability

The plugin publishes a portable Agent contract at
`stonebot://agent-contract`. It has two tool profiles:

- `full`: Codex or a Harness with a reliable multi-step tool loop.
- `compact`: weaker Harnesses, using `stonebot_advance_until_gate` at each
  explicit human gate.

Both profiles call the same `PluginJobService`, workflow state machine and
verification code.

The target adapter matrix is Codex, DeepSeek Harness, Claude Code and Kimi Code.
Codex and DeepSeek Harness are the current reference implementations. A new
platform is supported only after it passes the shared golden cases and delivery
policy; listing or invoking tools alone is not sufficient.

## Adaptive profile learning

A confirmed correction can create a project-scoped `ProfilePatch` candidate.
The patch records before/after values, evidence counts, the source job and the
target corrected counts. Candidate patches are stored under the plugin data
root and do not change the live profile.

After explicit user approval, `stonebot_accept_profile_patch`:

1. re-reads the source drawing with the base and candidate profiles;
2. compares panel, hole and number counts to the corrected target;
3. replays every available validated fixture for the same base profile;
4. rejects candidates that regress the current drawing or historical cases;
5. writes a versioned project profile override while leaving the base profile
   unchanged.

`stonebot_review_profile_patch` performs the same validation as a dry run and
writes a self-contained HTML review containing rule differences, current
drawing counts and historical replay results. Activation always revalidates.

For weak Harnesses, `stonebot_rename_panels` provides a direct multi-panel
numbering operation and builds the underlying `CorrectionPlan` internally.

New jobs in that project use a matching override by drawing fingerprint. An
override can be rejected or superseded without changing `drawing_profiles/`.
`stonebot_list_profile_overrides` exposes active overrides and activation
history; `stonebot_rollback_profile_override` restores the previous version or
the immutable base profile.

## Number ownership

Profile learning changes recognition rules, not the business mapping between a
label and a panel. When a drawing contains valid labels, Stonebot preserves the
label position/containment mapping even when panel discovery order differs.
Agents must not relabel panels by array order.

For the Snow White fixture the verified mapping is `p0=XST-4`, `p1=XST-1`,
`p2=XST-2`, `p3=XST-3`, `p4=XST-5` and `p5=XST-6`. A plugin-service regression
test locks this mapping. Automatic `P-*` numbering and explicit
`stonebot_rename_panels` calls are reserved for missing or user-confirmed
labels.

## Delivery policy

The plugin never treats its internal staging folder as a user deliverable. At
the final gate the Agent must call `stonebot_choose_output_directory`, which
opens a native folder picker. Canceling the picker leaves the job at the final
gate and writes no deliverable.
The selected absolute directory is then required by
`stonebot_finalize_job` (or by the compact final gate).

Default delivery is exactly two files:

1. the in-place numbered DXF;
2. the nested DXF.

No report file is generated by default. A Word report is produced only when
the user explicitly requests it, using a second user-selected directory and
`stonebot_export_word_report`. The DOCX writer is implemented with Python's
standard library so the plugin does not add an Office runtime dependency.

## Artificial-stone texture effect

After a job is completed, `stonebot_generate_textured_drawing` can project a
reusable artificial-stone pattern image onto the active nesting and write a
textured in-place DXF plus per-part PNG files and previews. The pattern image
covers the usable sheet area exactly and does not include the oversize
allowance. One pattern may be reused for every sheet of the mapped material.

This milestone does not support natural-stone per-sheet images, per-sheet
edge recognition or defect avoidance. Those belong to a separate future
workflow and must not be passed to the artificial-stone texture tool.

## Manual layout adjustment propagation

After completion, `stonebot_propagate_layout_adjustment` accepts a nested DXF
that the user saved after moving whole part GROUPs on one reference sheet.
The service:

- matches boards by sheet dimensions and the multiset of canonical part shapes;
- applies the reference sheet's relative translations to identical inventories;
- leaves part geometry, numbers, holes and rotations unchanged;
- validates bounds, overlap, label ownership and hole ownership before moving
  each target sheet;
- skips a target atomically when validation fails;
- writes a new DXF plus JSON manifest into a user-selected directory.

This never changes the sheet count and never edits the user's adjusted input.

## Circular-saw audit

`stonebot_audit_saw_clearance` audits an existing nested DXF without changing
it.  Given the blade diameter and sheet thickness, it calculates the half-chord
at `thickness + plunge_extra`, checks pronounced outer reflex cut points
against other parts on the same sheet, and returns:

- overall `safe` result and minimum neighbour clearance;
- sheet-level checked/insufficient counts;
- affected `part -> neighbour` pairs with coordinates and deficits;
- an explicit limitation note because this is not a full CAM simulation.

The same audit is available from the CLI:

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts\audit_saw_clearance.py `
  "排板.dxf" --diameter 350 --thickness 20 --fail-on-risk
```

## Isolation

Development uses a separate workspace copy so the stable working repository
remains on `master`. Plugin jobs use `STONEBOT_MCP_DATA_ROOT`; the default is
`output/mcp_jobs`, not the normal live output location.

## Current limitations

- MCP jobs use a versioned JSON/WKT context snapshot. Drawing parts, holes,
  correction revisions, nesting results, validation state and artifact paths
  can be restored after a process restart without pickling Shapely objects.
- The DSH adapter currently links to an external Python runtime; it is not yet
  a self-contained cross-machine Runtime package.
- Claude Code and Kimi Code adapters are planned targets, not completed
  integrations.
- Cloud profile-pack ingestion, validation, signing and rollback are not yet
  implemented.
- Cross-platform business-result conformance is the release gate; tool
  discovery alone is not considered successful integration.
