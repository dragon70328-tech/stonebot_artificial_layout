# StoneBot 产品方向

> 状态：当前产品与架构判断基准  
> 日期：2026-10-30  
> 适用范围：DXF 审图、原位修正、排板、画像学习、插件适配与部署

## 1. 一句话定位

StoneBot 是一个面向人造石加工、平台无关的 DXF 审图与排板运行时。它通过标准 MCP
协议和薄插件连接 Codex、DeepSeek Harness、Claude Code、Kimi Code 等对话平台，
让用户通过对话完成审图、修正和排板。

平台负责理解用户、发起工具调用和展示结果；StoneBot 负责识别、校验、修正、
排板、回滚和交付。任何平台都不能替代 StoneBot 的确定性业务闭环。

## 2. 对原目标的必要调整

| 原目标或默认假设 | 调整后的目标 |
|---|---|
| 以 SaaS 网页、CLI 或 `main.py` 作为主要产品入口 | StoneBot Runtime 是产品核心；CLI、Web、Codex、DSH、Claude Code、Kimi Code 都是入口 |
| 每个 Harness 分别组织业务流程 | 业务流程只在 StoneBot Core 实现，各平台只保留薄适配器 |
| 依赖 Agent 的 Observe -> Act -> Replan 保证质量 | 关键识别、校验、重试和回滚由 StoneBot 的确定性状态机完成 |
| 画像主要由开发者在项目中手工积累 | 用户确认的结构化纠正进入候选画像库，经回放验证后形成版本化画像包 |
| 插件目标是兼容 Codex 和 DSH | 目标是平台无关 MCP 契约和统一适配器规范，主流平台按能力接入 |
| 先用视觉模型或 Rhino 补读图 | 先完成确定性 DXF 解析、拓扑闭合、证据和校验；视觉只做低置信度增强 |
| SaaS 是唯一长期形态 | 同时支持本地 Runtime、公司私有服务和云端服务，共用同一核心 |

原有“AI 只生成结构化意图，真实执行由可信 Python 工具完成”的原则保持不变，并进一步
明确为：**业务闭环也属于 Python 核心，不属于任何外部 Agent。**

## 3. 分层架构

```text
Codex Adapter
DSH Adapter
Claude Code Adapter
Kimi Code Adapter
Web / CLI Adapter
        |
        v
Standard MCP Contract
        |
        v
StoneBot Runtime
  - workflow state machine
  - deterministic recognition
  - closure repair
  - nesting and validation
  - artifact lineage
  - profile learning
  - delivery policy
        |
        v
Versioned Drawing Profiles / Recognition Packs
```

### 3.1 StoneBot Core

核心必须独立于模型和 Harness，负责：

- DXF 解析、单位、图层、线型和实体分类；
- 图纸指纹与画像匹配；
- 线网拓扑、端点吸附、缝隙处理、闭合面提取；
- 编号、孔洞和材料归属；
- 原位 DXF 生成与回读验证；
- 桥切、水刀、激光排板；
- 几何、工艺、刀缝和交付硬校验；
- 有界重试、候选比较、回滚和标准错误码；
- 用户纠正证据、画像补丁和验证案例；
- 用户确认门和用户选择保存目录。

### 3.2 MCP Contract

MCP 是跨平台主协议，应同时支持：

- 本地 `stdio`；
- 远程 Streamable HTTP；
- 版本化 JSON Schema；
- 结构化状态、错误码、证据和下一步动作；
- `full`、`compact`、`minimal` 能力档位；
- 同一业务结果的一致性测试。

Agent 只消费工具契约和结构化结果，不读取或修改 StoneBot 内部源码。

### 3.3 Host Adapter

平台适配器只负责：

- 插件清单和安装方式；
- 启动或连接 MCP；
- 平台专用提示词和工具展示；
- 原生文件选择器；
- 认证、权限和会话桥接。

适配器不得复制审图、排板、画像或校验算法。

## 4. 两类闭环必须分开

### 4.1 模型交互闭环

```text
理解用户 -> 调用工具 -> 解释结果 -> 等待人工决定
```

不同平台的模型能力可能差异很大。该闭环影响对话体验，但不能成为业务正确性的唯一保障。

### 4.2 确定性业务闭环

```text
识别 -> 校验 -> 失败分类 -> 有限重试 -> 再校验
-> 候选比较 -> 人工门 -> 输出 -> 回读验证
```

该闭环属于 StoneBot Core，必须在 Codex、DSH 和其他平台上得到相同结果。

## 5. 审图闭环

审图闭环应覆盖：

1. 只使用符合画像和工艺规则的有效实线实体；
2. 区分真正缝隙与制造容忍范围内的绘图误差；
3. 支持非矩形区域的受控封口；
4. 在明确缝隙处断开，不能跨接；
5. 保留实体窄板，不把结构碎片当噪声；
6. 匹配原始编号并保证唯一归属；
7. 校验板块、孔洞、面积、尺寸、包含关系和重叠；
8. 生成原位 DXF 后重新读取并复算；
9. 有多个近似答案时输出候选和证据，不自动猜测；
10. 只有结构化校验通过后才进入 `audited` 人工门。

自动修正只能使用画像中允许的确定性操作，不能删除零件、改变编号真值或伪造通过状态。

## 6. 排板闭环

排板闭环必须验证：

- 件数不丢失；
- 零件尺寸和孔洞不被修改；
- 不越界、不重叠；
- 旋转、共边、最小间距符合工艺；
- 不同材料和工艺正确分组；
- 刀缝材料校验通过；
- 板数、出材率、尾板和切割可执行性按统一排序比较；
- 输出 DXF 回读后再次验证。

系统可以保证“交付布局合法且可复现”，不能承诺所有订单都达到理论最少板数。
无法找到合法布局时必须阻塞，不能通过放宽约束生成结果。

## 7. 画像与集体学习

用户纠正不能直接成为全局规则。正确流程是：

```text
结构化纠正
-> 候选反馈
-> 相似图纸聚类
-> 生成候选画像补丁
-> 当前图纸复算
-> 历史案例回归
-> 人工批准
-> 版本化画像包
-> 客户端更新
```

画像层级固定为：

```text
系统基础画像 < 公司画像包 < 项目画像覆盖 < 用户临时修正
```

默认只上传结构化、去标识化的识别证据。完整 DXF、客户信息和项目资料未经明确授权不得
进入公共学习库。云端学习的目标是丰富画像库，不是把所有图纸训练成一个平均画像。

## 8. 跨平台一致性

首批目标平台：

- Codex：完整开发、诊断、测试与生产对话入口；
- DeepSeek Harness：生产对话入口，能力较弱时必须使用服务端闭环；
- Claude Code：按平台插件与 MCP 能力提供薄适配；
- Kimi Code：支持 MCP 时直接接入，否则提供标准桥接器。

每个平台发布前都必须通过同一组黄金案例。只验证“工具能列出”不算通过，必须验证业务结果：

- 正确阻塞开放线网误识别；
- 正确识别已闭合的 1212 块图纸；
- 不丢失编号、孔洞和窄板；
- 排板无丢件、越界和重叠；
- 默认只交付原位 DXF 和排板 DXF；
- 保存目录必须由用户选择；
- 阻塞不能被包装成成功；
- StoneBot 会话不得调用 Rhino 或任意脚本绕过门禁。

## 9. 部署形态

### 9.1 本地 Runtime

适合单机和离线场景。正式安装包必须包含或锁定：

- StoneBot Core；
- 私有 Python Runtime；
- 依赖锁；
- 基础画像；
- 黄金案例；
- 版本清单和自检工具。

原始虚拟环境目录不能直接作为可迁移安装包。

### 9.2 公司私有服务

适合多台电脑共用同一版本、画像库和审计记录。客户端只连接受认证的远程 MCP 服务。

### 9.3 云端服务

适合跨组织更新公共画像包和提供可选学习服务。核心几何校验仍使用同一实现。

版本必须至少区分：

- `adapter_version`
- `core_version`
- `mcp_protocol_version`
- `profile_pack_version`
- `dependency_lock`

版本不兼容时必须拒绝运行，而不是降级为不可验证的自由 Agent 流程。

## 10. 交付与安全边界

- 业务交付默认只有原位 DXF 和排板 DXF；
- Word 排板报告仅在用户明确要求时生成；
- 最终文件不得自动保存到推断目录，必须使用原生目录选择器；
- StoneBot 不打开 Rhino，不通过 CAD 自动化补图；
- 不在生产会话中直接修改 Python 核心或画像文件；
- 登录态、租户、项目、画像和任务必须隔离；
- 日志和反馈不得无授权上传原始客户图纸。

## 11. 里程碑

### M0：失败即停止

当前已完成的基础：

- 无画像且编号归属为零时不自动编号；
- `skip_unnumbered` 旁路不再暴露给 Agent；
- `blocked` 以 MCP 工具错误返回；
- StoneBot 与 Rhino 的 DSH profile 隔离；
- 0.2.2 黄金回归通过。

### M1：核心确定性闭环

- 完成线网闭合、局部封口和缝隙规则；
- 完成审图与排板统一验证器；
- 完成有界重试、候选比较和回滚；
- 用真实图纸建立识别、排板和回读门禁。

### M2：统一 MCP 契约与首批适配器

- 稳定 `full / compact / minimal` 工具档；
- Codex 与 DSH 使用同一契约；
- 增加跨平台黄金案例和错误码一致性测试。

### M3：更多平台与 Runtime 分发

- 接入 Claude Code 和 Kimi Code；
- 提供版本化本地 Runtime 安装包；
- 支持远程 MCP 和公司私有部署。

### M4：画像包与集体学习

- 建立候选反馈接收、聚类和回归验证；
- 发布可签名、可回滚的画像包；
- 支持系统、公司、项目和用户四级画像。

## 12. 判断新需求的优先级

新需求应先回答：

1. 它属于 StoneBot Core，还是只属于某个平台适配器？
2. 它是否提高识别、排板或交付的可验证性？
3. 它是否减少用户纠正次数或阻止同类错误复发？
4. 它是否能进入确定性测试和历史案例回归？
5. 它是否扩大平台覆盖面而不复制业务逻辑？
6. 它是否符合人工门、用户选择路径和数据隐私边界？

不能通过确定性验证、不能回退或只能依赖某个 Agent 临场发挥的功能，不应进入生产关键路径。
