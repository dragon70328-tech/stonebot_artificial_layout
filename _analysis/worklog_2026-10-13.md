## 二、P0：会话接口可跨租户控制任务（已修）

### 缺陷

`POST /conversations/{conversation_id}/respond` 里所有 job 动作都走
`_resolve_conversation_job(conversation, intent)`，而该函数**只信任 `intent["job_id"]`**，
既不校验角色、也不校验任务归属：

```python
def _resolve_conversation_job(conversation, intent):
    job_id = intent.get("job_id") or conversation.job_id
    ...
    return str(job_id)
```

同一个文件的 `/jobs/{job_id}/*` 全部端点（以及 `/conversations/{id}/artifacts`）
都有 `_require_role(tenant, "operator")` + `_require_job_tenant(job_id, tenant)`，
只有会话 respond 分支漏了。后果：知道别的租户的 job_id 就能借会话接口
查询、确认、继续、回看、纠正、取消该任务。job_id 形如
`agent-<文件名stem>-<时间戳>`（`agent_runtime.py`），不是秘密。

### 修复（`src/http_api.py`）

1. `_resolve_conversation_job(conversation, intent, auth)`：解析出 job_id 后立即
   `_require_job_tenant(job_id, auth)`。校验放在解析处，6 个分支无法漏检。
   - 任务不存在 → 404（沿用 `_require_job_tenant` 语义）
   - 归属不符 → 403 `tenant mismatch`
2. 新增 `_CONVERSATION_ACTION_ROLES`，在 dispatch 前按同名 REST 端点的口径校验角色：
   `create_job / confirm_job / run_job / cancel_job / correct_drawing / review_job`
   需要 `operator`；`get_job` 与 `GET /jobs/{job_id}` 一致，不额外要求角色。
3. 无租户密钥配置（`STONEBOT_TENANT_API_KEYS` / `STONEBOT_API_KEY` 为空）时，
   `_require_role` / `_ensure_tenant_match` 照旧直接放行——单机开发模式行为不变。

### 回归测试（`tests/test_conversation_api.py`）

- `test_respond_rejects_job_of_another_tenant`：acme 用 intent 里的
  `job_id=job-conversation`（属 default）发起 `get_job` → 403 `tenant mismatch`，
  且未触达 manager；同一 intent 由 default 发起 → 202 且 `manager.got` 命中，
  证明拒绝的是归属而不是意图。
- `test_respond_requires_operator_role_for_job_actions`：viewer 角色 `cancel_job`
  → 403（含 "operator"），未触达 manager；同租户 `get_job` → 202，查询不被拦。

断言里的 `detail` 精确到具体守卫，避免测试因其他原因拿到 403 而假绿。

## 八、API/agent 路径接上同一套口径（用户"继续"后）

问题（9-29 遗留、本轮确认）：`validate_kerf_material` 只在命令行调用，
API/agent 的 job 流程从不做刀缝材料校验；而且排板空间取自工具参数
`sheet_width`（= 请求标称），契约里的 `SheetSpec.usable_*` 被忽略——
即声明"可利用尺寸 3185"也会按 3200 排。

修复（全部走同一口径：排板空间 = 可利用；校验允许 = 实物 = 标称 + 让尺）：

| 文件 | 改动 |
|---|---|
| `src/tool_handlers.py` | `nest_parts` 优先用 `SheetSpec.usable_*` 作为排板空间（无契约时回退工具参数）；新增 `_kerf_material_params()` / `_kerf_material_errors()`，在 `postprocess` 阶段做桥切刀缝材料校验（allowance = 标称 + 让尺 − 可利用），失败并入 `ctx.validation_errors` → `write_dxf` 拒绝出图；水刀/激光按 `ProcessPolicy.process != BRIDGE` 跳过；`write_report` 按契约写口径五件套 |
| `src/workflow.py` | `build_report` / `build_check_payload` 的 `sheet_dimensions` 增加 `physical_width/height`（实物 = 标称 + 让尺）与 `kerf_allowance_x/y_mm`（= 实物 − 可利用）；两者由标称/让尺/可利用推导，不再由调用方各算一遍 |
| `src/job_context.py` | 新增 `kerf_metrics` 字段（进 snapshot 的 nesting.kerf_material） |
| `src/tool_schemas.py` | `nest_parts` 描述写明排板空间来自契约可利用尺寸 |
| `src/conversation_planner.py` | 提示词补口径段：usable_* 是零件可用区、oversize 是给刀缝的实物余量、桥切会因 刀缝>让尺 被拦、水刀不计刀缝 |

设计要点：契约里利用尺寸可能小于标称（修边等），所以 allow 用
`标称 + 让尺 − 可利用`，而不是只加让尺；这样三种情形都自洽——
可利用=标称 → 允许让尺；可利用=标称+让尺 → 允许 0（零件已吃满）；
可利用<标称 → 允许整块剩余板面 + 让尺。
