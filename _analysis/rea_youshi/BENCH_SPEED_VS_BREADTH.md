# 实测：我们的一次布局有多贵 / 我们的"广度"有没有用

日期：2026-10-14　目的：判断"有石CAD 那种廉价多轮重启"能否搬到我们
"最少大板数"的目标上。全部用 CGR45final.dxf（203 件，`:3200x1800`）冷启动实测。

## 1. 单次布局成本

```text
python main.py "<CGR45final.dxf>" 3200 1800 20 --cold-start --drawing-profile cgr45 \
    --no-beam --quick --budget 0 --report-only --no-confirm
```

| 指标 | 数值 |
|---|---|
| 墙钟总耗时 | 25.1 s |
| 其中排板耗时 | **17.6 s** |
| 结果 | 52 张大板 / 70.15%（复现历史基线） |
| `_default_configs` 配置数 | 10 |
| → **单次布局成本** | **≈1.78 s**（203 件 → ~114 件/s） |

## 2. 现有"广度"实测（10 trials）

```text
... --no-beam --quick --budget 0 --trials 10 --report-only
```

| 指标 | 数值 |
|---|---|
| 实际评估布局数 | 10 trials × 10 configs = **100 次** |
| 秒数 | 177.7 s（≈1.78 s/次，与上表吻合） |
| 结果 | **52 张大板 / 70.15%（与单次完全一致）** |

结论：**100 次重排全部收敛到同一答案 → 我们现在没有真正的"重启多样性"。**
原因（`src/nesting.py:528-542`）：

```text
10 个配方 = 7 个完全固定（short/area/long × skyline/col/contact）
          + 3 个 "jitter"（仅 面积降序 × U(0.9,1.1) 噪声）
--trials 只重掷这 3 个 jitter 的 randrange 种子
```

对照有石CAD `DeepNest`（`Nester.cs`）：随机扰动**排序键（4 种：最大边长/面积/最长边/反向）
+ 放置模式（BlMode/BlAxisMode/SheetStrategy）+ 保留前缀、重排尾部**，最多 30 轮。
扰动强度差一个量级。

## 3. 推论

- **广度在墙钟上负担得起（小单）**：203 件时 1.78 s/次 → 3 分钟可跑 ~100 次；
  1543 件的 citizen 是 54 s/次（540 s / 10 configs）→ 100 次要 90 分钟。
  → 大单上"广度"的瓶颈是**常数**，不是算法结构。
- **目标函数口径要改**：现排序键是"板数最少，其次制造评分/紧凑度"，
  **尾板填充没进排序键**；有石CAD 则把"利用率 + 人工挑方案"当验收。
  最少板数是离散目标、有平台期，真正的分界在"尾板那几件能不能并出去"。
- 不能把"人工挑方案"当搜索的一部分（SaaS 要自动、可复现、可审计），
  必须用 `(板数, 尾板填充, 总浪费)` 顶替人眼。

## 4. 附：CGR45 @3200x1800 为什么"50 张"固定不住（实测条件矩阵）

全部为 2026-10-14 本机实测，输入 `CGR45final.dxf`（203 件），冷启动。

| 条件 | 板数 | 出材率 | 排板耗时 | 回看结果 |
|---|---:|---:|---:|---|
| `--no-beam --quick --budget 0`（纯贪心多配置） | 52 | 70.15% | 17.6 s | 未跑 |
| `--trials 10 --no-beam --quick --budget 0`（=100 次布局） | 52 | 70.15% | 177.7 s | 未跑 |
| `--report-only`（任意宽度） | 51 | 71.52% | 317 s | **根本未跑**（报板数即停） |
| `--quick`（beam 400）+ 回看 | **51** | 71.52% | 166.8 s | 未发现可合并的板 |
| `--profile min_sheets`（beam **1000**）+ LNS 60s + 回看 | **50** | **72.95%** | 322.0 s | 减 sheet [40] |
| 同上，第二次独立运行 | **50** | 72.95% | 322.3 s | 减 sheet [40]（完全一致） |

结论：

1. **50 张是"束搜索把尾板排到只剩一件、回看再并掉那一张"的产物**，不是算法不变量。
   宽度降到 400（`--quick`）→ 尾板不干净 → 回看看不出可并的板 → 51。
   开关在 `src/workflow.py:648`：`beam_width = beam_width or (400 if quick else 1000)`。
2. `--report-only` 会跳过回看 → 停在 51。用这个看板数会误判"定不住"。
3. 回看与 LNS 都是**墙钟时间预算制**（`nesting_reviewer.py` 的 `time.monotonic()` deadline、
   `--review-budget 120s` / `per_donor_time_s=20s`；`nesting.py:583` 的 `budget_s`）→
   机器更慢/更忙时，即使布局相同也可能来不及并掉 sheet [40] → 51。本机两次 322.0/322.3 s
   完全一致，说明当前环境安全，但**没有机制保证**。
4. 排序键目前是"板数最少，其次制造评分/紧凑度"，**尾板填充没有进排序键** →
   50 是撞上的，不是搜出来的；没有任何目标在引导"尾板干净"。
5. 49 张无人证明不可行（面积下界 37）。"固定在 50"是工程目标，不是最优性结论。

## 5. 附：NFP 在我们真实图纸上的收益面上限（形状统计）

脚本：`_analysis/rea_youshi/cgr45_shape_and_fill.py`（按轮廓边方向统计，长度加权）。

| 图纸 | 板数/出材率 | 轮廓边长合计 | **轴对齐** | 含斜边件 | 平均顶点数 |
|---|---:|---:|---:|---:|---:|
| CGR45final（203 件） | 50 / 72.95% | 946.3 m | **99.9%** | 37 / 203（36 件是小圆角弧） | 8.8 |
| citizen ST-6（1543 件） | 148 / 87.62% | 12 738.0 m | **100.0%** | **0** | 5.1 |

含义：NFP 的独门能力是**斜边/弧边互锁**，而这两单几乎没有斜边可利用；
轴对齐件的可行放置点本身就是轴对齐角点集合，"空闲矩形减法 + 束搜索"的表达能力
已接近 NFP。→ **为降板数而引入 NFP 属于错配投资**。

缺口的性质（两单不一样）：

| | CGR45 | citizen ST-6 |
|---|---|---|
| 距下一档 | 49 张需平均 74.44%（现 72.95%，**+1.5pp**） | 147 张需平均 88.21%（现 87.62%，+0.59pp） |
| 填充分布 | 最低 67.4% / 中位 81.5% / <60% **0 张** → **没有可并的干净尾板** | 尾板 42.9% 与 55.7%（很肥）/ 其余中位 86.5% |
| 每板件数 | 3~7 件，件长 1.1~3.1 m | 中位 **12 件 = `_MAX_PIECES_PER_SHEET` 硬上限** |
| 板数杠杆 | **跨板重组**（清空某张板），不是贴合度 | 放开每板件数上限 + 跨板重组 |
