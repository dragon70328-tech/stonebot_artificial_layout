## 二、严重缺陷：束搜索超预算静默丢件（已修复）

### 现象

首次排板（`--budget 60`，修复前代码）结果：**16 张板 / 出材率 95.61% /
"校验通过"**——但理论最少 130 张。排板 DXF 里只有 **176 件**（16 张 × 11 件，
版式几乎逐张相同），**1367 件被静默丢弃**，报告 `total_part_area` 只有
78.33 m²（应为 663.92 m²），且全流程无任何报错。

### 根因（e32e71f 引入）

1. `nesting.py` 给 `beam_layout` 传了 `time_budget_s=improve_budget`，
   注释写"超出预算后由 greedy_fallback 收尾，结果仍完整"，
   **但调用时没传 `greedy_fallback`**；
2. `beam_nesting._beam_pass` 在预算耗尽且无 fallback 时直接 `break`，
   返回**部分布局**（citizen 量级下束搜索每张板约 3-4s，60s 预算只够 ~16 张）；
3. 部分布局按"板数优先"评分**反而最优**，成为最终布局；
4. 下游只有几何校验（重叠/越界），**没有任何环节核对"输出件数 == 输入件数"**。

为什么测试没拦住：既有夹具量级小（CGR45 等），束搜索在默认 180s 预算内
能排完，不会触发截断分支；酒店 ST-201 走矩形快通道，不经过束搜索。

### 修复

| 位置 | 内容 |
|---|---|
| `src/nesting.py` | 束搜索调用补上 `greedy_fallback`（确定性 area/skyline 贪心收尾）；最终布局落地前校验"输出件数 == 输入件数"，不符直接 RuntimeError |
| `main.py` | 后处理/回看之后的总校验里追加零件总数核对（发现丢失并入 validation_errors，阻止出图） |
| `tests/test_beam_budget_completeness.py` | 3 例：fallback 完整性、无 fallback 部分返回契约、nest_parts 端到端完整性 |

验证：`pytest -q -m "not slow"` **513 passed / 7 skipped**（原 510 + 新 3）。

### 教训（写进流程）

- 任何"预算截断"的实现，**截断分支必须显式处理剩余量**；注释声称的保证
  要在调用点核实，不能只看 docstring。
- 排板结果的**完整性（件数/面积）必须像几何合法性一样强制校验**；
  "校验通过"不能只指重叠/越界。
- 用户报"怎么这么少板/出材率异常高"时，先核对件数再谈优化。

### 分级横带原型（未采用）

另写了独立原型：按短边分档横带 + 行内面积目标子集和 + 按行高装箱，
毫秒级出结果，但 **185 张 / 71.0%**，明显劣于经典引擎。原因是
1600 高与 622.3/571.5 档不能整除，纯横带会留下 355mm 空带，而经典引擎
的 skyline/contact 能跨档互锁。**结论：这座图的板数对"跨档互锁"很敏感，
不能为了速度退回纯横带。**

### 时间问题的真正位置

2036s 中：束搜索约 1900s、LNS 70s、压缩 9s。束搜索的每层开销由
"空闲矩形 × 23 个尺寸档 × 取向变体"决定，与 beam_width 近似无关；
1543 件 × 152 张板的深度遍历才是主因。下一步可做（按收益排序）：

1. **尺寸档裁剪**：23 档里有 9 档件数 ≤ 22，合并后可把每层候选数砍掉一半；
2. **每板件数上限**（`_MAX_PIECES_PER_SHEET=12`）现在正好卡在中位数上，
   放开到 20+ 可减少板数也可能减少总层数，需 A/B；
3. **两遍法（refine_tail）只在小尾板时开启**：大单一律第一遍即可；
4. 增量缓存：同尺寸档的板模式按（剩余档向量）签名缓存，跨板复用。

## 八、可复现性验证（2026-10-21）

用户问"现在的算法能否多次复现相同结果"。实测三次独立运行
（同一 DXF、同一命令 `--budget 180 --beam-budget 0 --beam-width 1000
--pattern-reuse 4 --cold-start`）：

| 运行 | 板数 | 排板耗时 | 几何指纹 |
|---|---:|---:|---|
| 20261021_183555（10 套贪心 + 两遍） | 148 | 1634.4s | `472a40c7...800` |
| 20261021_201450（1 套贪心 + 跳过第二遍） | 148 | 262.1s | `472a40c7...800` |
| 20261021_202601（同 201450 命令复跑） | 148 | 282.4s | `472a40c7...800` |

几何指纹 = 每张板内零件多边形坐标（2 位小数）+ 编号文本位置，按板排序后
SHA-256。**三次完全一致**；DXF 文件逐行比较 183,874 行中仅 20 行不同，
全部是 AutoCAD 元数据（`$TDCREATE` 儒略日、两个 GUID、LAYOUT 句柄），
与排板结果无关。

10-14 首版同是 148 张，但几何指纹不同（`5a6623...346`）——那是旧引擎
（无板型复用、两遍法）的产物，属于版本差异，不属于随机性。

### 会破坏可复现性的三个时间相关分支

1. `--budget N`（LNS 墙钟护栏）：触发时报告 `lns_budget_exhausted=true`，
   结果依赖机器速度；本次 18 轮/12 轮无改进提前停，未触发；
2. `--beam-budget N`（N>0）：束搜索按墙钟截断 + 贪心收尾；
   **要稳定请用 `--beam-budget 0`**；
3. 多板尾解 `_beam_pack_multi` 的 20 秒 deadline：超时会退回逐板求解。
   已新增 `parameters.optimizer.multi_tail_attempts / multi_tail_success /
   multi_tail_timeout` 三个统计，超时会在报告里留痕。

排板核心本身是确定性的：`random.Random(seed)` 全部显式播种，几何排序与
状态去重都不依赖 `PYTHONHASHSEED`（`hash()` 只作用于浮点元组，不受字符串
哈希随机化影响），核心路径没有多线程/多进程。

## 九、并行分批（2026-10-21 晚）

用户问："多规格板分批、多线程同时排，会不会提速？"

### 先纠正一个前提

排板是纯 Python 计算，**多线程被 GIL 卡住**，必须用多进程。

### 分批的代价（同一材料内切批）

按尺寸档分层轮转切批（顺序切会规格失衡），只跑束搜索那层：

| 批数 | 每批件数 | 总张数 | 单批最长耗时 |
|---:|---|---:|---:|
| 1 | 1543 | 148 | 100.2s |
| 2 | 777 / 766 | 150（+2） | 55.6s |
| 3 | 523 / 515 / 505 | 151（+3） | 46.8s |

每批都留一张自己的尾板，这是 +2/+3 的来源。

### 实现

`src/parallel_nesting.py` + `workflow.nest_groups_parallel` + CLI
`--parallel-workers N`：

1. **按材料分组并行**（零损失：不同材料本来不能共板）；
2. 同一材料 >500 件且 workers>1 → 按尺寸档分层切批；
3. **尾部合并**：每批取最低填充的一张板，重新拼进更少的张数；
4. 多进程不可用时自动退回顺序执行（stats 记 `parallel_fallback`）；
5. 并行模式自动回看默认限时 60s（默认无限时会在大单上跑很久）。

### citizen ST-6 验收（3 批）

| 项目 | 结果 |
|---|---|
| 首批 3 批合计 | 149 张 |
| 尾部合并 | 0 张（3 个尾板拼不进 2 张） |
| 自动回看 | **-1 张**（sheet[149]） |
| 最终 | **148 张 / 87.62%**，与单批完全一致 |
| 后处理 | 靠边/通切/间距全部达标 |
| 校验 | 1543 件、越界 0、重叠 0、编号一致 |

本次沙箱禁止创建多进程管道（`PermissionError WinError 5`），实际按顺序
跑 3 批：排板 361.3s、回看 61.8s、整单 587.7s。**真机多进程可用时**，
排板段约为单批最长值（约 120s，含每批贪心），整单预计 4~5 分钟。

### 结论

- 分批本身能提速（束搜索 100s → 47s），但**每批的贪心/校验开销不随批量缩小**，
  所以整单收益是 20~30%，不是 3 倍；
- 尾部合并 + 回看能把张数补回 148，做到**零材料损失**；
- 真正免费的是**按材料并行**，这条应当默认使用。

### 补：顺序兜底的错误（用户指出）

用户明确指出"顺序跑完 3 批就没有分批的必要"。这是对的，而且原实现确实
会在多进程不可用时仍分批顺序跑：citizen 实测 **149 张 / 361s**，比单批
**148 张 / 262s** 更差——纯亏。

修正：

1. `src/parallel_nesting.probe_multiprocessing()`：开跑前创建一个小进程池探测；
2. `main.run`：探测失败 → 打印"本次按单批排板，不做分批"并把 workers 置 1；
3. `workflow.nest_groups_parallel`：同样前置探测（API 调用也受保护），
   stats 记 `parallel_unavailable`；
4. `scripts/check_parallel.py`：一条命令自检本机能否多进程。

本沙箱探测结果：`CPU 逻辑核 32 / 多进程不可用（PermissionError）`，
因此本地只能验证"退回单批"这条路径（雪花白 6 件冒烟正常，515→519 测试全过）。

### 诚实的收益评估

| 场景 | 张数 | 整单耗时 | 结论 |
|---|---|---|---|
| 单批（基线） | 148 | 357s | — |
| 3 批真并行（推算） | 148 | ~270s | 约 25% 提升 |
| 3 批顺序（本沙箱） | 149 | 588s | **明确劣化，已禁止** |
| 多材料并行 | 零损失 | 接近 ÷材料数 | **真正值得默认** |

原因：每批的贪心/LNS/校验固定开销不随批量缩小；回看与后处理是单线程固定
成本（约 90s + 60s），批数再多也省不掉。
